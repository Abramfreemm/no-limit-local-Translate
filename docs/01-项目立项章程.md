# 01 · 项目立项章程（Project Charter）

## 1. 项目背景

市面上的文档翻译方案存在三处结构性痛点：

1. **隐私不可控**：DeepL / Google / 各类 AI 翻译都要求把文档上传到第三方服务器。合同、病历、财报、未公开技术资料一旦上传，合规风险就已产生。
2. **按量付费且有上限**：云翻译按字符计费，PDF 通常按页计费，且普遍存在单文件页数、体积、并发限制（常见 10–50 页 / 20 MB 上限），大部头书籍与长报告根本无法处理。
3. **排版破坏**：通用翻译工具把 PDF 当纯文本处理，公式、多栏、图表、目录、脚注全部错位，译后几乎不可读。

与此同时，本地推理生态已经成熟：用户机器上的 **Ollama** 能以极低门槛运行 `translategemma`、`qwen3` 等高质量开源多语言模型；OCR 侧也有 RapidOCR / PaddleOCR 这类完全离线、CPU 可跑、许可证宽松的方案。**把这两者与一套自研的文档版面重建流水线拼起来，就能得到一个"不上传、不计费、不限制页数"的翻译器。**

## 2. 项目目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 全链路离线 | 断网状态下完成一份 200 页 PDF 的 OCR + 翻译 + 排版重建；进程外发流量为 0（用防火墙/抓包验证） |
| G2 | 无页数与体积限制 | 1000 页 / 500 MB PDF 可完整跑完；不出现 OOM，不出现"文件过大"类拦截 |
| G3 | 排版可用 | 学术论文、产品手册、多栏报告三类样本，人工评审"无需二次调整即可阅读"比例 ≥ 80% |
| G4 | 覆盖主流格式 | 至少 12 种输入格式；PDF/DOCX/PPTX/XLSX 保持结构输出 |
| G5 | 门槛低 | 用户只需已装 Ollama；首次启动引导拉取模型，3 步内完成第一次翻译 |
| G6 | 双平台交付 | 产出 Windows `.exe` 安装包与 macOS `.dmg`，均可双击安装/拖拽安装 |

### 成功标准（验收门槛）
- 断网可用，且 1000 页 / 500 MB 样本跑通（G1+G2 是**一票否决项**）
- PDF 保排输出在 3 类样本上人工评分 ≥ 3.5 / 5
- 冷启动到首屏 ≤ 5 s（不含模型加载）
- Windows 安装包与 macOS dmg 均可在一台干净机器上完成安装并成功翻译一个样例文件

## 3. 范围界定

### 3.1 范围内（In Scope）
- Windows 10/11 x64 与 macOS 12+（Apple Silicon 与 Intel 双架构）桌面端
- PDF / DOCX / PPTX / XLSX / EPUB / HTML / MD / TXT / SRT / VTT / CSV / ODT / RTF / 图片的读取
- 扫描件与图片类 PDF 的离线 OCR
- 通过 Ollama 调用本地大模型翻译；支持自定义系统提示词、术语表、翻译记忆
- 双语对照 / 纯译文 / 可搜索 PDF / 原格式回填 四类输出
- 任务队列、断点续翻、批量处理
- 简体中文与英文界面（后续可加）

### 3.2 范围外（Out of Scope）—— 明确不做
- **不内置任何大模型权重**（安装包不捆绑 GB 级模型；模型由 Ollama 管理）
- **不做云端翻译后端**（不接 DeepL / Google / OpenAI 官方 API，保持纯离线定位）
- 不做移动端（iOS / Android）、不做浏览器插件、不做 Web 服务
- 不做协同编辑、不做账号体系、不做付费与授权服务器
- 不做手写体高精度识别（仅尽力而为）
- V1.0 不做扫描件的"完全像素级还原"（那属于版面重排的研究课题，V1.0 目标是"可读 + 结构正确"）

### 3.3 约束与前提
- **前提**：用户机器已安装 Ollama（本项目检测而非代替安装；未安装时给出下载指引）
- **硬件下限**：8 GB 内存（16 GB 推荐）；OCR 与翻译均可纯 CPU 运行，有 GPU 时 Ollama 自动加速
- **磁盘**：应用本体约 250–400 MB；翻译模型由 Ollama 另占 3–20 GB
- **许可证底线**：不使用任何 AGPL / 非商用许可证的运行时依赖（详见 09）

## 5. 主要风险（立项层面）

| 风险 | 影响 | 缓解策略 |
|---|---|---|
| PDF 原位回填排版效果不及预期 | 高 | V1.0 同时提供"保排 PDF"与"Markdown 降级"两条输出路径；排版不好时用户仍有可用产物 |
| macOS 未签名导致 Gatekeeper 拦截 | 中 | 文档提供 ad-hoc 签名 + 右键打开指引；正式分发建议购买 Developer ID |
| Ollama 未启动或模型缺失 | 中 | 启动自检 + 一键 `ollama pull` + 明确的错误引导，不做静默失败 |
| 翻译大模型输出不稳定（漏翻、加戏） | 中 | 编号化批量输入 + JSON 结构化输出 + 长度校验 + 失败自动重试与降级拆分 |
| 打包体积与启动速度 | 低 | 按需导入、延迟加载 OCR 后端、去掉未用 Qt 模块 |

## 6. 立项结论建议

**建议立项**。技术路径上的三个关键环节（Ollama 翻译、离线 OCR、PDF 版面重建）均已有成熟、宽松许可证的开源方案可直接复用，不存在需要自研模型的科研风险；真正的工作量集中在"版面重建 + 大文件流式工程化 + 双平台打包"三项工程实现上，属于可控范围内的确定性工作。

预估总工期（v2.0 重估）：**0.1.0 = 10 人日**，**0.2.0 = 8 人日**，合计 18 人日。

原「精简版 3 周 / 标准版 6–7 周」的双路线已作废 —— M0–M5 实际早已完成，真正的缺口不是「功能不够」，而是「没有工程门禁、失败无引导、大文件未验证」。故改为按版本切：0.1.0 补门禁/错误码/日志/安全/失败恢复（可发给别人用），0.2.0 补内存/UI/验收（能扛大文件）。详见 06 号与 22 号。
