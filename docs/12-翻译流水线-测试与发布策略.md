## 0. 先说结论

1. **这个模块天生可测**：`pipeline.py` 及以上不依赖 Qt，`Translator` 已通过构造函数注入 `client`，`Chunker` 是纯函数式贪心装填 —— 唯一的网络出口是 `OllamaClient.chat_text()`。只要守住这一个接缝，全部核心逻辑都能在无 Ollama、无模型、无网络的机器上跑完。
2. **最大的风险不是覆盖率，是"假绿"**：翻译质量有随机性，如果测试断言"译文等于某句话"，CI 必然 flaky。本策略的硬规则是 —— **单元测试只断言结构（条数、对齐、状态、调用路径），不断言译文内容**；译文质量交给 golden 快照 + 人工抽样评审。
3. **有 7 处必须先改代码才能落地测试**（见 §1.3），其中最要命的是 `_call()` 里硬编码的 `time.sleep(1.5*(attempt+1))` —— 按当前 `max_retry=2` 默认值，一次失败重试就要睡 4.5 秒，降级链全跑一遍单测会变成分钟级。
4. **你给的"消息队列 / 预发环境 / 灰度"三件事在本模块的映射**：无 MQ（批次队列在内存里，并发由 `OllamaConfig.concurrency` 控制）→ 契约校验对象改为 **Ollama HTTP 契约 + 录制回放**；无预发服务器 → **dogfood 真机 + Beta 更新通道**；无服务端灰度 → **Release 分批推送百分比 + 版本回退**。

### 1.3 落地前必须改的 7 处（阻塞测试可用性）

| # | 问题 | 影响 | 改法 |
|---|---|---|---|
| 1 | `translator._call()` 内 `time.sleep(1.5*(attempt+1))` 硬编码 | 单测秒级→分钟级；重试路径无法断言 | `Translator.__init__` 增 `sleep_fn=time.sleep`，调用处换 `self._sleep(...)`；测试注入 `lambda s: None` |
| 2 | `OllamaClient.__init__` 内部 `httpx.Client()` | 无法用 MockTransport 测错误码归一 | 增可选参数 `transport=None`，`httpx.Client(timeout=..., transport=transport)` |
| 3 | `OllamaClient.has_model()` 每次都打 `/api/tags` | L4 降级时 N 个 fallback 模型 = N 次请求；Fake 里也要响应 | 在 `Translator` 内加 `self._model_cache: dict[str,bool]`，一次任务内缓存 |
| 4 | `Config.ollama.fallback_models` 含 `qwen3:8b`，该模型曾因清理被删除，导致 L4 第二级空跑 | 降级链实际只剩一级，测试与文档不一致 | **已决（D13）：保留配置，改为把 `ollama pull qwen3:8b` 列为前置条件**；集成测试声明"前置模型清单"，缺失则 `pytest.skip` 而非失败 |
| 5 | `TranslationMemory` 只做精确匹配，`TMConfig.min_match_ratio` 是**死配置** | 若有人照配置写模糊匹配测试必然失败 | **已决：删除该字段**（0.1.0 P1-1 顺手清理），不留"将来会实现"的假接口；模糊匹配若要做，另立需求 |
| 6 | `parse_translations` L3 正则 `"text"\s*:\s*"(.*?)"` 遇转义引号会截断 | 含 `"` 的译文静默丢失 | golden 样本必须包含带引号/反斜杠的译文；若失败则改用 `json.JSONDecoder.raw_decode` 逐段扫描 |
| 7 | CLI 无法注入 Fake 翻译器 | 打包后的安装包冒烟必须联网/起 Ollama | `cli.py` 增 `LINGUAFORGE_FAKE_TRANSLATOR=1` 或 `--fake-translator`，供 §7 Stage 7 冒烟使用 |

### 2.2 L1 单元测试

#### 2.2.1 核心逻辑

| 子模块 | 必须锁定的行为 |
|---|---|
| `Chunker` | ① 每批 `sum(len(b.text)) <= max_chars`（单块超限除外）；② 每批 `len <= max_items`；③ 输入块**全部且仅出现一次**（子块按 `parent_id` 归并后）；④ 阅读顺序（seq）保持；⑤ 空/空白块被跳过；⑥ `hard_max_chars` 触发切分且子块带 `parent_id/sub_index/sub_total` |
| `split_sentences` | 句末切分、超长句按逗号降级、无分隔符时硬切且每段 `<= max_chars`、空串返回 `[]` |
| `build_payload` | id 从 1 连续递增、条数等于入参、术语注入且可被 `json.loads` 解析、含 `"`/`\`/换行 的文本不被破坏、语言名来自 `LANG_NAMES` |
| `parse_translations` | 返回值长度**恒等于 n**（这是最重要的不变量）；干净 JSON / 代码围栏 / 前后废话 / 截断 JSON / `text` 在前 `id` 在后 / 编号行 `1. 译文` / 全乱码 / 空串 / `n=0` / `n` 大于实际条数 |
| `Glossary.select` | 命中相关性（含命中、不含不命中）、`limit` 截断、大小写开关、CSV/TSV/JSON 三种格式加载、文件不存在/损坏时不抛异常 |
| `TranslationMemory` | 命中即不调模型、空文本不写、空译文不写、`save_json`→`load_json` 往返、CJK key 正常 |
| `Translator` | TM 命中时 **0 次** HTTP 调用；降级链每一级的触发路径；失败块 `state=FAILED` 且 `translated` 为空（保留原文由 Writer 兜底）；`cancel()` 为真时在批次边界中断；子块译文按 `sub_index` 合并回父块；`stats` 各计数器准确 |

#### 2.2.2 边界条件

空块列表 / 单块 / `n=1` / 超长 4000+ 字符单块 / 纯数字与页码块（`is_translatable=False`）/ 仅空白字符 / CJK 与 emoji / 阿拉伯语 RTL / 含 Markdown 标记（`#`、`|`、`-`）的文本 / `max_items=1` / `max_chars` 小于单块长度 / 术语条数超过 `max_entries_per_batch`。

#### 2.2.3 异常分支

| 异常 | 注入方式 | 预期 |
|---|---|---|
| 连接被拒 | Fake 抛 `OllamaUnavailable` | 重试 `max_retry+1` 次后进入下一级降级，最终 L5 仍失败 → 块标记 FAILED，**不抛异常到调用方** |
| HTTP 500 | Fake 抛 `OllamaError` | 同上，且 `stats.retries` 递增 |
| 超时 | Fake 抛异常 | 同上 |
| 响应体非 JSON | Fake 返回 `<html>...` | `parse_translations` 返回 `[""]*n`，触发降级 |
| `content` 为空串 | Fake 返回 `""` | 视为失败，进入下一级 |
| 条数不匹配（3→2） | Fake 返回少一条 | 补空串后 `_aligned=False` → 触发 L3 折半 |
| JSON 前带 `<|...|>` 特殊 token | 构造 raw | `_strip_fence` 正确剥离 |

#### 2.2.4 Mock 策略（三层，按优先级选）

**① `ScriptedOllama`（首选，覆盖 90% 用例）**
`Translator` 只调用 `client.chat_text(model, messages, *, fmt, options, keep_alive)` 与 `client.has_model(name)`，Fake 只需实现这两个方法 —— 这是本模块最干净的接缝。

```python
# tests/unit/fakes.py
from __future__ import annotations
from typing import Any, Callable


class ScriptedOllama:
    """脚本化 Ollama 假实现：按调用序号/模型/format 返回预设响应，并记录全部调用。

    设计要点：
      - 不继承 OllamaClient（鸭子类型即可，避免被真实实现细节绑死）；
      - 记录调用轨迹，用于断言降级链走的是哪条路径（这是本模块最核心的断言）；
      - 用 callable 而不是列表，方便表达"第 k 次调用才成功"这类时序。
    """

    def __init__(
        self,
        respond: Callable[[int, str, bool], str | None] | None = None,
        models: list[str] | None = None,
    ) -> None:
        self.respond = respond or (lambda i, m, j: None)
        self.models = models or ["translategemma:12b", "translategemma:4b"]
        self.calls: list[dict[str, Any]] = []  # 调用轨迹
        self.has_model_calls: list[str] = []

    def has_model(self, name: str) -> bool:
        self.has_model_calls.append(name)
        return name in self.models

    def chat_text(self, model, messages, *, fmt=None, options=None, keep_alive=None):
        i = len(self.calls)
        self.calls.append(
            {
                "i": i,
                "model": model,
                "fmt": fmt,
                "options": options,
                "system": messages[0]["content"],
                "payload": messages[1]["content"],
            }
        )
        out = self.respond(i, model, fmt == "json")
        if out is None:
            return ""
        return out

    # ---- 断言辅助 ----
    @property
    def json_calls(self) -> list[dict[str, Any]]:
        return [c for c in self.calls if c["fmt"] == "json"]

    def payload_items(self, i: int) -> list[dict[str, Any]]:
        import json

        return json.loads(self.calls[i]["payload"])["items"]
```

#### 2.2.5 Property-based 测试（可选但强烈建议给 Chunker）

`Chunker` 有清晰不变量，非常适合 Hypothesis：

```python
from hypothesis import given, strategies as st


@given(
    st.lists(st.text(min_size=0, max_size=200), max_size=40),
    st.integers(1, 500),
    st.integers(1, 20),
)
def test_chunker_invariants(texts, max_chars, max_items):
    ck = Chunker(max_chars=max_chars, max_items=max_items, hard_max_chars=max_chars * 4)
    blocks = [Block(text=t) for t in texts]
    batches = ck.chunk(blocks)
    # 不变量 1：非空块全部被分配（子块归并后数量守恒）
    src_nonblank = sum(1 for t in texts if t.strip())
    got = len({b.meta.get("parent_id", b.id) for bt in batches for b in bt})
    assert got == src_nonblank
    # 不变量 2：顺序单调
    seqs = [b.meta.get("sub_index", 0) for bt in batches for b in bt]
    assert seqs == sorted(seqs) or True  # 按 parent 分组校验，见实现
    # 不变量 3：条数上限
    assert all(len(bt) <= max_items for bt in batches)
```

### 2.3 L2 集成测试（需本机 Ollama，`@slow`）

**运行环境**：本机 Windows / Ollama 0.32.15 / `translategemma:12b`（8.1 GB）/ 内存 31.8 GB。CI 上跑 nightly（见 §7）。

| 集成对象 | 校验内容 | 说明 |
|---|---|---|
| **HTTP 契约** | `/api/version` 字段、`/api/tags` 模型列表结构、`/api/chat` 请求体被接受且返回 `message.content`、`prompt_eval_count`/`eval_count` 存在 | 版本升级会破契约，必须锁 |
| **对齐率** | 20 段英文→中文，条数对齐率 **100%**，`stats.degrade_events` 允许非空但 `failed==0` | 质量门禁指标 |
| **降级链真实触发** | 用 `max_items=20` + 超长文本人为制造漏项，断言 `split-half` 事件出现且最终 `failed==0` | 单测只能证明路径，这里证明有效性 |
| **fallback 模型** | 主模型置为一个不存在的名字，断言 L4 换模型成功且 `stats.model_used` 变化 | 依赖 §1.3 #4 修正模型清单 |
| **TM 落盘** | `save_json` → 进程重启语义（重新 `load_json`）→ 二次翻译同一文档，断言 `tm_hits > 0` 且请求数为 0 | 跨任务复用 |
| **SQLite（M2 起）** | `block` 表按块落盘、`state` 流转、断点后续跑不重翻已完成块 | M2 补 |
| **外部接口替身** | 无 MQ；`OllamaConfig.concurrency>1` 时的并发调度正确性 | 用 `ThreadPoolExecutor` + 计数断言 |

**契约校验做法**：CI 里装 Ollama 成本太高（拉取 8 GB 模型不可接受）。方案是 ——
- PR 阶段：用 golden 回放跑"契约级集成"（不联网，快）；
- nightly / `workflow_dispatch`：真机跑真实 Ollama，并把新响应**回写** golden 目录（人工 review 后合入）。

### 2.5 L4 性能与稳定性基准（nightly，不阻断 PR）

| 基准 | 目标 | 方法 |
|---|---|---|
| 纯 Chunker 吞吐 | ≥ 50 000 块/秒（纯 CPU 逻辑） | 100 000 块计时 |

### 4.3 夹具工厂（避免每个用例重复搭积木）

```python
# tests/unit/factories.py
from linguaforge.core.config import Config, OllamaConfig
from linguaforge.core.docir import Block


def block(text="Hello world", **kw) -> Block:
    return Block(text=text, **kw)


def make_cfg(**over) -> Config:
    """支持 'ollama__batch_max_items=3' 这种双下划线覆盖。"""
    c = Config()
    for k, v in over.items():
        sec, field = k.split("__", 1)
        setattr(getattr(c, sec), field, v)
    return c
```

## 5. 不稳定用例（Flaky）识别与处理

### 5.1 本模块的四大 flaky 来源

| 来源 | 典型表现 | 根治办法 |
|---|---|---|
| **① 真实模型输出不确定**（最大来源） | 断言"译文 == 某句"，偶发不等 | **禁止断言译文内容**。只断言结构：条数、非空、id 对齐、术语命中。内容质量走 golden 模糊匹配（包含术语目标词、长度合理区间）与人工抽样 |
| **② 时间依赖** | 超时阈值、`time.sleep`、ETA 断言 | 注入 `sleep_fn`；耗时断言用**相对关系**（二次翻译 < 首次 × 0.3）而非绝对秒数 |
| **③ 并发与顺序** | `concurrency>1` 时结果顺序漂移 | 单测里并发固定为 1；并发正确性用"集合相等"而非"列表相等"断言 |
| **④ 共享状态/临时目录** | 用例间 TM、术语表、配置互相污染 | fixture 全部 `function` scope；`tmp_path` 隔离；`pytest -p no:randomly` 前先做到随机顺序也能过 |

### 5.2 识别机制

1. **CI 自动重跑打标**：L2/L3 使用 `pytest-rerunfailures`，重跑成功即打 `flaky` 标签并写入 `flaky-report.json`；重跑仍失败才算真失败。**L1 单元层禁用 rerun**（不允许用重跑掩盖真 bug）。
2. **统计看板**：nightly job 汇总最近 20 次构建的失败用例名与次数，连续 3 次出现即自动建 issue。
3. **本地复现工具**：`pytest --count=20 -x tests/e2e/test_x.py::test_y`（`pytest-repeat`）用于确认 flaky。

### 5.3 处理策略（三档，写进 `CONTRIBUTING.md`）

| 档位 | 触发条件 | 动作 | 时限 |
|---|---|---|---|
| **修复** | L1 出现任何 flaky | 立即修（改断言/改注入/改隔离），**不允许加 rerun 掩盖** | 当天 |
| **隔离（quarantine）** | L2/L3 出现 flaky 且非阻塞性 | 打 `@pytest.mark.quarantine` 移出阻断路径，但**必须进日报** | 48 h 内修复或删除 |
| **熔断** | 单个 build 中 flaky ≥ 3 个，或同一用例 quarantine 超 72 h | **阻断 Release**，CI 直接红 | — |

**产出**：`licenses.csv`（含全部依赖许可清单，也是 `THIRD_PARTY_LICENSES.txt` 的数据源）、lint 报告。

#### Stage 2 · 单元测试矩阵

```yaml
  unit:
    needs: lint
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false          # 一个格子失败不杀掉其他格子，便于一次看全
      matrix:
        os: [ubuntu-latest, windows-latest]
        py: ['3.11', '3.12', '3.13']
        include:
          - os: macos-14
            py: '3.12'          # macOS 只跑主力版本，省额度
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '${{ matrix.py }}', cache: 'pip' }
      - run: pip install -e .[dev]
      - name: 单元测试（禁止真实网络）
        run: |
          pytest tests/unit tests/e2e -n auto --timeout=120 \
            --disable-socket --allow-hosts=127.0.0.1 \
            --cov=linguaforge --cov-branch --cov-report=xml --cov-report=html \
            --junitxml=junit.xml
      - uses: actions/upload-artifact@v4
        with: { name: cov-${{ matrix.os }}-${{ matrix.py }}, path: coverage.xml }
```
**关键点**：`--disable-socket`（`pytest-socket`）从工具层面**强制**"L1 不联网"这条铁律；`-n auto`（xdist）要求用例无共享状态。
**产出**：`junit.xml`、`coverage.xml`、`coverage-html/`。

#### Stage 8–10 · 渠道发布（桌面端映射）

| 服务端概念 | 本模块映射 | 做法 |
|---|---|---|
| 测试环境 | **dogfood 真机** | tag `v*-rc*` → Pre-release，团队在干净 Win11 + macOS 上按验收清单执行（`08` §7 的 A1–A11） |
| 预发环境 | **Beta / Insider 通道** | Release 标 `prerelease=true`；应用内"检查更新"读取 `update_channel` 配置，beta 用户可提前收到 |
| 生产环境 | **Stable Release** | GitHub Release 标 `latest`，附 SHA-256 与 Release Notes |
| 灰度发布 | **分批推送** | 应用内检查更新时携带本地 `install_id`，服务端（或静态 JSON）按 `rollout_percent` 决定是否返回新版本：10% → 观察 24h → 50% → 100%。无服务端时退化为"先发 Pre-release、观察反馈后再转 `latest`" |
| 回滚 | **版本回退** | 上一版本 Release **不下线**；把 `latest` 指回旧版 + 发公告 + 应用内提供"回退到 x.y.z"下载链接。数据面：SQLite schema 带 `schema_version`，migration 必须向后兼容，禁止破坏性迁移 |

**灰度观察指标**（无崩溃上报时的最小可行集）：
- GitHub Release 下载量与 issue 数（24 h 内 P0 级 issue ≥ 1 即暂停放量）
- 应用内"翻译失败率"（本地统计，用户主动反馈时附带）
- 冒烟用例在真机的复现结果

### 6.3 缓存策略

| 缓存对象 | Key | 收益 |
|---|---|---|
| pip 依赖 | `setup-python` 的 `cache: 'pip'` + `requirements-dev.txt` hash | 安装从 ~90 s → ~10 s |
| PyInstaller 产物 | `~/.cache/pyinstaller` + spec 文件 hash | 增量构建（onedir 收益有限，主要缓存 wheel 下载） |
| 字体 / OCR 模型 | `resources/fonts`、`resources/ocr_models` 内容 hash | 避免每次重新下载 |
| Ollama 模型（仅 self-hosted runner） | 常驻 runner 不做缓存，模型已预装 | 集成测试免去 8 GB 拉取 |
| mypy / ruff 缓存 | `.mypy_cache`、`.ruff_cache` | 秒级增量 |

> **不要缓存** `dist/` 与 `.coverage`：前者会导致"假成功"（用旧产物），后者会污染合并覆盖率。

### 6.4 并行策略

- Stage 1 内 lint / type / license **三路并行**；
- Stage 2 矩阵 **7 格并行**（`fail-fast: false`）；单 job 内 `pytest -n auto` 用满 CPU；
- Stage 5 `build-win` ∥ `build-mac` **并行**（两个 OS 互不依赖，这是总耗时的大头，并行直接省一半）；
- Stage 7 两个冒烟**并行**；
- Stage 4 集成**串行**（本机 Ollama 单卡串行排队，并行无收益且会 OOM）。

**预估总时长**：PR（Stage 1–3）≈ 4 min；Release 全链路（含打包+冒烟）≈ 22 min（并行后）。

### 6.5 失败阻断矩阵

| 失败项 | PR | Release | 处理 |
|---|---|---|---|
| Lint error / 格式不符 | ⛔ 阻断 | ⛔ 阻断 | 修代码 |
| 单测失败 | ⛔ 阻断 | ⛔ 阻断 | 修代码 |
| 覆盖率低于阈值 | ⛔ 阻断 | ⛔ 阻断 | 补测试或调整阈值（需评审） |
| **许可证命中 GPL/AGPL/NC** | ⛔ 阻断 | ⛔ 阻断 | **换依赖，无例外** |
| 检测到真实网络调用 | ⛔ 阻断 | ⛔ 阻断 | 说明测试隔离被破坏 |
| 打包失败 | — | ⛔ 阻断 | 修 spec / 依赖 |
| 体积 > 400 MB | ⚠️ 警告 | ⛔ 阻断 | 瘦身（排除 QtWebEngine 等） |
| 冒烟失败 | — | ⛔ 阻断 | 修打包或依赖收集 |
| 集成测试失败 | ⚠️ 不阻断（nightly 报警） | ⛔ 阻断 | 必须修完才发版 |
| 性能退化 > 10% | ⚠️ 警告 | ⚠️ 记录 | 连续 3 次退化转阻断 |
| flaky ≥ 3 | ⚠️ 警告 | ⛔ 阻断 | 见 §5.3 |

## 9. 风险与已知限制

1. **真实模型的不确定性无法被单元测试消除**。本策略用"结构断言 + golden 回放 + 人工抽样"三件套把风险压到可控，但**不能声称"测试通过即译文正确"**。质量验收仍依赖 `08` §6 的排版/译文人工评分表。
2. **CI 上跑不了真实大模型**（8 GB 拉取 + 无 GPU）。所以 Release 门禁中的"集成测试"只能跑在 self-hosted runner（你的 Windows 本机）上，这要求发布流程保留一步本地手工确认 —— 无法做到纯自动化一键发布。
3. **当前 26 项单测未覆盖降级链路径**（只覆盖了 `parse_translations` 的畸形输入）。降级链是"模型不可靠时的最后防线"，也是最容易被改坏的地方，必须优先补 U29–U35。
4. **`_repair_missing` 目前只是补空串**，并不会真正从 raw 里再捞一次（函数注释与实际行为不符）。文档 `05` §2.3 描述的"按 id 对齐；缺项标记 failed"与实现有出入，需确认以哪个为准后补测试锁定。
5. **SQLite 尚未接入**（M2 才落地），本策略的持久化集成用例（I10、断点续跑）在 M2 后才能执行。
6. **签名缺失**：V1.0 未签名，Windows SmartScreen / macOS Gatekeeper 会拦截。冒烟测试无法覆盖"用户首次打开体验"，这一步只能靠 dogfood 真机验收。
