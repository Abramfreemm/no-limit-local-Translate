## 0. 本文档的作用

`08` 给了目标值（如"内存 ≤ 1.5 GB"），但没给**来源分解**与**回归门槛**。结果是：数字达标了不知道为什么达标，超标了不知道超在哪。

本文档给出三样东西：
1. **预算表**：每个指标的来源拆解（体积由谁贡献、时间耗在哪）；
2. **容量模型**：给定页数与格式，估算耗时与内存的公式；
3. **回归门槛**：CI 里怎么卡住性能退化。

## 2. 体积预算（真实分解）

安装后 436 MB 的构成（`dist_v2/LinguaForge/_internal/`，`du -sm` 实测）：

| 组件 | MB | 占比 | 是否可减 |
|---|---|---|---|
| **cv2（OpenCV）** | **112** | 25.7% | **可减 60–80 MB**（见 §2.1） |
| PySide6 | 94 | 21.6% | 可减（已排除 WebEngine；Qt3D/Quick 已排除） |
| resources（字体 38 + OCR 模型 13） | 51 | 11.7% | 字体可子集化到 ~6 MB |
| onnxruntime | 43 | 9.9% | 难减（OCR 必需） |
| numpy.libs | 21 | 4.8% | 难减 |
| rapidocr_onnxruntime | 14 | 3.2% | 难减 |
| PIL | 13 | 3.0% | 可减（去掉未用的插件） |
| cryptography | 10 | 2.3% | **可能可减**（见 §2.2） |
| pypdfium2_raw | 8 | 1.8% | 必需 |
| pdfminer | 8 | 1.8% | 必需 |
| numpy | 7 | 1.6% | 必需 |
| lxml | 7 | 1.6% | 必需 |
| 其余 | ~48 | 11% | — |

### 2.1 cv2 是最大单项，且很可能是浪费

`requirements.txt` 只声明了 `opencv-python-headless`，但本机环境同时装了 `opencv-python` 与 `opencv-python-headless`（各 5.0.0.93，见 10 号 P1）。打包时若两者共存，`cv2` 目录会包含两份二进制与多余的 ffmpeg DLL（本次 dist 里可见 `opencv_videoio_ffmpeg500_64.dll`）。

**核对结果**：本次 dist 内 `cv2/` 下没有 Qt 相关文件，说明最终装进去的是 headless 版（非 headless 版会带 `plugins/platforms/`）。因此**未发生重复打包**，112 MB 是 headless 版本身的体积（OpenCV 5.x 单包就很大）。

**优化路径**（V1.1 评估，勿在 V1.0 动）：
- 只用到灰度/二值化/去噪/旋转，`opencv-python-headless` 可换成 `Pillow + numpy` 手写（约 +40 MB → -100 MB），但需重写预处理并重测 OCR 精度。
- 净收益约 −70 MB，风险是 OCR 精度回退。**ROI 一般，排在最后。**

### 2.2 cryptography 10 MB 的来源存疑

`requirements.txt` 里没有 `cryptography`。它是某个依赖的传递依赖（可能是 `httpx` 的某个 extra 或 `pdfminer.six` 的可选加密支持）。10 MB 不是大问题，但**来历不明本身就是问题**——依赖树需要能解释每一项。

**动作**：V1.0 内跑一次 `pipdeptree -r -p cryptography` 定位引入者，若无人真正使用则从 spec 的 `excludes` 中排除。

### 2.3 字体 38 MB → 目标 12 MB

当前 `resources/fonts/` 放了三个文件：
```
NotoSansSC.ttf        17.8 MB  （可变字体，已被 fontTools 实例化）
NotoSansSC-Regular.ttf 10.6 MB
NotoSansSC-Bold.ttf    10.6 MB
```
可变字体原文件在实例化后**不再需要**，可删除（−17.8 MB）。两份静态字体若要进一步减，需按实际用字做子集（中文常用字 3500 → 约 3–5 MB/份）。

**动作**：V1.0 内删除可变字体原件（改 `prepare_resources.py` 在实例化后不保留），净减 17.8 MB，零风险。

## 3. 时间模型

### 3.1 分阶段实测

| 阶段 | 单位耗时 | 来源 |
|---|---|---|
| 解析（文本 PDF） | **27 ms/页** | 本次 1000 页实测（23,700 块） |
| 解析（20 页小文件） | 50 ms/页 | 本次实测（含每页固定开销摊薄少） |
| 页面渲染 200 DPI | 150 ms/页 | M0 |
| OCR（CPU） | 1,930 ms/页 | M0 |
| 翻译（12B 模型，热态） | 900 ms/条 × 批量 3 条/请求 ≈ 2.7 s/批 | M0/M1 |
| PDF 回填写出 | 未单独测 | — |

### 3.2 容量模型（用于 UI 的 ETA 与磁盘预估）

```
总耗时 T ≈ Σ_pages ( T_parse + [T_render + T_ocr] + T_translate_per_page + T_render_out )

其中：
  T_parse        = 0.027 s           （文本页）
  T_render+T_ocr = 2.08 s            （仅扫描页）
  T_translate    = 0.9 s × 每页块数  （按每页约 20 块估算 ≈ 18 s/页）
  T_render_out   = 0.05 s（估）
```

**举例（用于验证模型是否可解释实测）**：

| 样本 | 页数 | 类型 | 模型估算 | 实测 |
|---|---|---|---|---|
| 20 页技术手册 | 20 | 文本 | 20 × (0.027 + 0.9×20.6) ≈ 371 s | **51.6 s** |

**模型高估 7 倍。原因**：M1 实测的 51.6 s 里，翻译走了**批量**（412 块合并为约 35 批 × 2.7 s ≈ 95 s？仍不匹配）。

真实原因是 **TM 命中 325 条**（样本重复率高），只有 87 块真正送模型。这说明：

> **ETA 不能用"块数 × 单条耗时"算。必须先算 TM 命中率再估。**

修正模型：
```
T_translate_per_page = 0.9 s × (每页块数 × (1 − TM命中率)) / 批量大小
```

**这是 UI 上 ETA 准确性的关键**，也是当前实现里最容易出错的地方（进度条走完了但还要等很久，或反之）。

### 3.3 三类用户的真实等待时间（诚实告知）

| 场景 | 解析 | OCR | 翻译 | 合计 |
|---|---|---|---|---|
| 300 页文本 PDF → 中文 | 8 s | — | 视模型 30–90 min | **30–90 min** |
| 900 页扫描手册 | 24 s | **29 min** | 60–180 min | **1.5–3.5 h** |
| 12 份 DOCX（共 200 页） | 6 s | — | 20–60 min | **20–60 min** |

**结论**：这个产品的时间成本是**小时级**。UI 必须：
1. 开始前给出预估值（不是"预计几分钟"这种含糊话，是"约 1 小时 40 分"）；
2. 允许关闭窗口后继续跑（托盘常驻）或明确说"关闭会中断，可续跑"；
3. 不承诺"快速"。**诚实告知时长是产品可信度的一部分**（见 14 号 §5.3）。

## 4. 内存模型（本次最重要的发现）

### 4.1 解析阶段：已达标，且余量巨大

**1000 页 / 23,700 块实测**：

| 采样点 | RSS |
|---|---|
| 进程基线（已 import） | 79.8 MB |
| 第 100 页 | 88.7 MB |
| 第 500 页 | 88.8 MB |
| 第 1000 页 | 89.4 MB |
| **峰值** | **89.4 MB** |

**RSS 随页数完全平坦（+0.7 MB / 900 页）**。这是流式架构（`iter_pages` 生成器 + 逐页落库）有效的直接证据，也是相对 pdf2zh（整份载入）的结构性优势。

对照 `02` §4 的"1000 页峰值 ≤ 1.5 GB"：**实测只用掉预算的 6%**。

### 4.2 真正的内存风险不在解析，在这三处

本次测的是**解析**。以下三处尚未测，且从代码看风险更高：

| 位置 | 机制 | 风险 |
|---|---|---|
| **二进制输出格式** | `pipeline._BINARY_FMTS = {docx, pptx, xlsx, srt, vtt}` 走"收集完整文档再一次性落盘" | **内存随页数线性增长**。1000 页 → 全部块对象驻留内存 |
| **SQLite 写入累积** | 逐页 `commit_every_pages=5`，但有 `block` 表全文缓存与索引 | 中（受 SQLite 页缓存影响） |
| **UI 预览** | `image_cache_pages=3` 的位图缓存，200 DPI 单页约 15 MB | 低（有 LRU） |

**必须补的测试**：
- T-1：1000 页 → DOCX 输出的峰值 RSS（预期是当前最大风险点）
- T-2：1000 页扫描件 → OCR + 翻译全链路峰值
- T-3：500 MB 单文件（当前样本只有 0.3 MB，未验证大文件 I/O）

### 4.3 本次测试的边界（必须写明，不能夸大）

- 样本是 **20 页 × 50 次复制**得到的 1000 页，文件仅 **0.3 MB**（内容重复，压缩率高）。
- 因此**只验证了"页数"维度，未验证"文件体积"维度**。
- 真实 500 MB 扫描件会带来：文件 I/O 压力、PDF 交叉引用表解析耗时、页面对象分散导致的随机读。这三项本次未覆盖。
- 结论表述应为：「1000 页解析内存已达标」，**不能说「A2 大文件验收通过」**。

## 5. 性能回归门槛（进 CI）

| 指标 | 门槛 | 检测方式 |
|---|---|---|
| 解析 1000 页耗时 | ≤ 60 s | 本文件同款脚本，CI nightly |
| 解析峰值 RSS 增量 | ≤ 200 MB | 同上 |
| 核心 import 时间 | ≤ 2 s | `python -X importtime` 断言 |
| 单页解析（20 页样本） | ≤ 80 ms/页 | 单测内计时，超时 skip 并告警 |
| 安装包体积 | ≤ 400 MB | CI 检查产物大小（已有） |
| 安装后体积 | ≤ 500 MB | 新增检查 |

**准入门槛**（不是提示，是阻断）：
- 连续 3 次 nightly 退化 > 10% → 阻断下一次发版（对应 12 号 §6.5）。

## 6. 降档策略（内存超阈值时自动执行）

`PerfConfig.memory_warn_mb = 1500` 目前只是**配置项，没有执行代码**（见 15 号技术债 T-）。

设计如下（V1.0 补实现）：

| 触发 | 动作 | 用户可见 |
|---|---|---|
| RSS > 60% 阈值（900 MB） | 释放预览位图缓存、GC | 无感 |
| RSS > 80% 阈值（1200 MB） | 渲染并发 2 → 1；跳过预览缓存 | 状态栏「内存偏高，已降低并发」 |
| RSS > 阈值（1500 MB） | 暂停当前任务，落盘当前进度，提示「内存不足，已暂停。可继续（将自动分段处理）」 | 黄条 + 继续按钮 |
| 超过 2× 阈值 | 中止任务，保留已译内容 | 红字 + 「查看原因」 |

**原则**：宁可降速、暂停，也**不允许 OOM 崩溃**——崩溃会让用户丢掉全部进度感知（即使数据还在 SQLite 里）。
