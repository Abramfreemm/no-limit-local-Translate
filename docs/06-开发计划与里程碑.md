## 2. 版本路线（v2.0 定稿）

| 版本 | 定位 | 范围 | 工作量 | 出口 |
|---|---|---|---|---|
| **0.1.0** | 敢发给别人用 | P0 门禁 · P1 错误码 · P2 可观测 · P3 安全 · P4 失败恢复 | **10.0 人日** | A1/A3/A5/A6 通过；15 号 §2.3 六条一票否决全满足 |
| **0.2.0** | 能扛大文件、界面统一 | P5 内存护栏 · P6 UI token · P7 依赖升级 · P8 验收发版 | **8.0 人日** | A2a/A2b + A4 排版评分通过 |

任务卡见 `22-0.1.0开发任务卡与验收清单.md`（每张卡 0.5–1.5 人日，含真实文件路径与验收命令）。

**为什么不是「一次做完 V1.0」**：单人开发的真实风险不是「做得不够多」，而是「做了 6 周还没人用过」。0.1.0 用 10 人日换到一个可安装、不闪退、失败有指引的包，先拿真实反馈；P5/P6 是规模与一致性问题，晚两周不致命。

**为什么 P4（失败恢复）排在 P5/P6 之前**：内存护栏影响的是 900 页以上任务的体验，失败恢复影响的是**每一次**首次使用。后者决定用户会不会有第二次。

## 3. 0.1.0 施工顺序与依赖

```
P0-1 CI 门禁 ──┬─→ P0-2 依赖锁定
               ├─→ P1-1 Problem ──┬─→ P1-2 合并 ParseError
               │                  ├─→ P1-3 PipelineResult ──→ P1-4 UI 文案 ──→ P4-1 预检查 ──→ P4-2 健康条
               │                  ├─→ P3-2 超时/尺寸
               │                  ├─→ P3-3 zip/像素
               │                  └─→ P3-4 文件名/no_proxy
               └─→ P2-1 日志 ──→ P2-2 异常钩子

P3-1 临时目录（无依赖，可随时插）
```

**关键路径**：`P0-1 → P1-1 → P1-3 → P1-4 → P4-1 → P4-2`，共 6.0 人日。其余可并行或插空。

**不可并行的原因**：P1-3 改了 `PipelineResult.errors` 的类型，P1-4 依赖新类型；P4-1 的错误码要先存在。任何试图「先做 UI 再补错误码」的顺序都会导致 UI 写两遍。

## 5. 每个任务的完成定义（DoD）

一张卡算完成，必须同时满足：

1. 代码改动已提交，提交信息符合 Conventional Commits（20 号 §2.1）
2. 新增/修改的行为有对应单测，`pytest -q` 全绿
3. 卡里写的**验收命令实跑过**，输出贴进 PR 描述
4. 涉及文档契约变更的，同步改对应文档章节（接口 → 05，错误码 → 19，门禁 → 12）
5. 当日工作记入 `.workbuddy/memory/YYYY-MM-DD.md`

**不算完成的情形**：代码写了但没跑验收命令；测试写了但没断言；「本地跑过，CI 应该也没问题」。
