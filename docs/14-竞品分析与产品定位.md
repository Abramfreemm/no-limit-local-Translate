## 0. 必须先接受的结论

**如果这个产品只做「PDF 保排翻译」，它会输给 PDFMathTranslate（pdf2zh）。**

理由不是我们做得差，而是对手的起点不同：

| 维度 | pdf2zh（1.x / next 2.x） | 我们 |
|---|---|---|
| 版面检测 | DocLayout-YOLO（ONNX 模型，专门训练过）判定正文/公式/图表区域 | 启发式：字号聚类 + 列检测 + 位置规则 |
| 社区 | 37.3K stars、3.3K forks、2026-10-03 仍在更新、EMNLP 2025 demo | 单人项目，0 用户 |
| 入门成本 | `pip install pdf2zh`，或下载 Windows zip 双击 | 需先装 Ollama 再装我们 |
| 翻译后端 | 默认可接 Google/Bing（免费、无需密钥） | 必须本地 Ollama |

**在"读一篇英文论文"这个场景上，pdf2zh 已经赢了，而且赢得合理。**

所以本产品的定位不能是"更好的 PDF 翻译器"，必须是**在 pdf2zh 覆盖不到的地方建立优势**。下面第三节给出这个"覆盖不到的地方"具体是什么。

## 1. 竞争格局分层

```
第一层 · 云服务（上传即翻译）
  DeepL Pro / Google 文档翻译 / Microsoft Translator / 腾讯翻译君 / 有道文档翻译
  特征：质量高、免部署；代价是必须上传 + 有硬性大小/页数/次数限制

第二层 · 开源保排工具（本地运行，PDF 专用）
  PDFMathTranslate (pdf2zh 1.x) / pdf2zh-next (BabelDOC) / MinerU
  特征：免费、保排好；代价是 AGPL 许可 + 命令行/WebUI + 只做 PDF

第三层 · 通用本地 LLM 前端（本地运行，非文档专用）
  Ollama + Open WebUI / LobeChat / Cherry Studio / AnythingLLM
  特征：隐私好；代价是不懂文档结构，PDF 进去是纯文本出来

第四层 · 浏览器插件（半本地）
  沉浸式翻译 / 彩云小译
  特征：网页体验极好；代价是文档能力弱、仍依赖云端

我们所在的位置：第二层与第三层之间 —— 有保排能力的桌面产品，且许可宽松、格式不限
```

## 3. 定位：我们不和 pdf2zh 抢"论文阅读"

### 3.1 pdf2zh 的三个结构性空白

**空白一：许可**
AGPL-3.0 意味着任何把它集成进产品的公司，都必须把自己整个产品的源码以 AGPL 开放。这对"想在企业内部做一个翻译工具"的团队是硬墙。**这不是技术问题，是法律问题，技术上无法弥补。**

→ 我们能提供的：Apache-2.0，企业可以拿去做内网工具、可以二次开发、可以不再开源。

**空白二：范围**
pdf2zh 只做 PDF。而真实用户的一天是这样的：早上翻一份 PDF 报告，中午翻一批 DOCX 合同，下午翻一版 PPTX 提案，晚上翻一集 SRT 字幕。他要装四个工具吗？

→ 我们能提供的：一次安装、一套术语表、一个队列处理全部格式。**术语和翻译记忆跨格式共享**是 pdf2zh 结构上做不到的（它没有 TM，也没有非 PDF 的解析器）。

**空白三：长任务**
pdf2zh 是"整份处理"：读入整个 PDF → 版面分析 → 翻译 → 输出。900 页扫描件会让它吃满内存，中途崩了就从头再来。

→ 我们能提供的：逐页流式 + SQLite 落盘 + 断点续翻 + 内存护栏。**这是架构第一约束，不是功能点。**

### 3.2 定位陈述（一句话）

> **给需要处理"大、杂、密"文档的人：一个装上就能用、不限页数、离线、能把 PDF / Office / 字幕一起翻完的桌面工具。不要你上传，不要你买额度，不要你装 Python。**

三个限定词都很重要：
- **大**：页数不设限、断点续翻 → 对应空白三
- **杂**：多格式、术语与 TM 跨格式共享 → 对应空白二
- **密**：不能上传（合同、病历、未公开资料）→ 对应第一层云服务的硬伤

### 3.3 定位图（二维）

```
        保排质量高
             ↑
   pdf2zh ●  │  ● pdf2zh-next
             │
             │        ★ 我们的目标位置
             │
  ───────────┼──────────────────→ 格式覆盖广
             │
  沉浸式翻译 ●│  ● 通用 LLM 前端
             │
        DeepL ●（云，上限硬）
             ↓
        保排质量低
```

**关键判断**：我们的目标位置在"格式广 + 保排中上"，**不在**"保排最高"。和 pdf2zh 比保排是打不赢的仗，只会拖垮进度。

## 4. SWOT

| | 有利 | 不利 |
|---|---|---|
| **内部** | **S1** Apache-2.0 许可，企业可用<br>**S2** 架构上不限页数（逐页流式 + 断点）<br>**S3** 多格式 + 术语/TM 跨格式共享<br>**S4** 双平台安装包，双击即用<br>**S5** 完全离线，零外发 | **W1** 无版面检测模型，保排靠启发式<br>**W2** 依赖用户自装 Ollama（门槛）<br>**W3** 单人开发，社区为零<br>**W4** UI 未经真实用户检验<br>**W5** 无签名证书，安装有拦截警告 |
| **外部** | **O1** 企业"数据不出内网"需求刚性上升<br>**O2** 本地模型质量仍在快速提升（Ollama 生态）<br>**O3** pdf2zh 的 AGPL 把商业用户挡在门外<br>**O4** 无一款产品把"多格式 + 离线 + 不限页数"做全 | **T1** pdf2zh 若改许可（如双许可），S1 优势消失<br>**T2** 云服务持续降价、放宽限额<br>**T3** Ollama 生态变化（API 变更、模型下架）<br>**T4** 大厂推出内置离线的办公套件翻译 |

### 4.1 对 T1 的预案（必须提前想）

如果 pdf2zh 转向宽松许可，我们的 S1 消失。此时护城河只剩 S2/S3/S4。判断：
- S2（不限页数）是**架构决定**，pdf2zh 要改需要重写流水线，短期内不会做；
- S3（多格式）是**范围决定**，他们要做得新增 6 个解析器；
- S4（安装包）是**产品化决定**，他们偏工程工具。

所以即使 T1 发生，我们仍有位置 —— 但位置会变窄。**这意味着"多格式 + 长任务"必须在 V1.0 就做扎实，不能留到 V1.1。**（这条直接影响 15 号路线图）

## 5. 定价与商业模式

### 5.1 事实约束

本项目是本地工具，**没有服务端成本**，也就没有按量计费的基础。同时它是开源（Apache-2.0），源码可获取。

### 5.2 可选的四种模式

| 模式 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| A 完全免费 + 自愿赞助 | GitHub Releases 免费下载，放赞助入口 | 传播最快、与开源一致 | 无收入 | **V1.0 采用** |
| B 免费 + 付费安装包 | 源码免费，签名/打包好的安装包收费（如 ¥39 一次性） | 覆盖签名证书成本 | 与 Apache-2.0 有张力（源码免费即可自行打包）；国内用户接受度低 | V1.1 评估 |
| C 开源核心 + 商业版 | 核心开源，企业版加审计日志/批量调度/集中术语库 | 企业市场有付费意愿 | 需要维护双版本 | V2.0 评估 |
| D 技术支持/定制 | 面向企业做私有化部署与定制 | 单价高 | 与单人开发冲突 | 机会性接单 |

**V1.0 结论：模式 A**。理由：当前阶段的目标是**获得真实用户与反馈**，不是收入。收费会显著降低试用意愿，而这个产品最缺的就是"有人真的用它翻完一份 900 页的手册"。

### 5.3 与云服务的单位成本对比（用于对外说明）

| 场景 | DeepL Individual | 我们 |
|---|---|---|
| 300 页技术手册（约 45 万字符） | 超出 30 万字符/月额度，需升 Team（€24.99/月）或分月翻 | 一次性 0 元 + 电费 |
| 900 页扫描手册 | 单文件超 30 MB 需 Business（€49.99/月） | 0 元，但耗时数小时 |
| 12 份 DOCX 合同 | 3 个/月额度不够，需 Business（100 个/月） | 0 元 |

**诚实的另一面**：我们消耗的是用户自己的时间与电费。900 页扫描件在本机 CPU 上跑可能 3–6 小时，而 DeepL 是分钟级。**这个劣势必须在产品里显式告知（预估耗时），不能藏。**

## 6. 护城河评估（自评，不打高分）

| 潜在护城河 | 强度 | 能否被复制 | 结论 |
|---|---|---|---|
| Apache-2.0 许可 | 中 | 竞品改许可即可消除 | 有效但会消失，不依赖它做长期规划 |
| 不限页数架构 | 中强 | 需重写流水线，成本高 | **真实护城河，必须守住** |
| 多格式 + 共享术语/TM | 中强 | 需新增多个解析器 | **真实护城河** |
| 设计系统与体验 | 弱 | 易复制 | 不构成护城河，但影响留存 |
| 社区与文档 | 弱（现在为零） | — | 需要时间积累 |

**坦率结论**：当前没有强护城河。产品能活下来的前提是**在 pdf2zh 不愿做的三件事（多格式、长任务、可商用许可）上做到"明显更好用"，而不是"功能列表更长"**。
