# 03 · 技术选型与可行性分析

版本 v1.0 ｜ 调研基准日：2026-10-21

## 1. 选型总原则

1. **许可证优先**：不使用 AGPL / GPL / 非商用（NC）许可证的运行时依赖 —— 我们要分发闭源自选的安装包，许可证传染是致命风险（详见 09）。
2. **能离线**：所有能力必须在断网下可用，模型与字典随包分发或预缓存。
3. **能打包**：必须有 pip wheel、无外部可执行依赖（不依赖 Poppler、Tesseract 二进制、LibreOffice）。
4. **CPU 可跑**：不假设用户有 NVIDIA GPU；有 GPU 时由 Ollama 自行加速。
5. **够轻**：OCR 相关依赖控制在几十 MB 级，不引入 PyTorch / PaddlePaddle 作为默认路径。

## 2. 应用框架选型

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **PySide6（Qt for Python）** ✅ 推荐 | LGPL-3.0（动态链接安全）；单进程同时跑 UI 与计算；PyInstaller / Nuitka 打包成熟；原生跨平台外观；信号槽天然适合进度回调 | 安装包体积 +80 MB 左右；UI 精致度需自己打磨 | **采用** |
| Tauri 2 + Python 子进程 | 体积小（~10 MB）、UI 现代（Web 技术栈） | 需 Rust 工具链；Python 侧要起 sidecar 进程并设计 IPC；macOS 打包与签名更复杂；调试链路长 | 备选（若你对 UI 颜值要求极高） |
| Electron + Python 子进程 | 生态最大 | 体积 150 MB+，内存占用高；同样有 IPC 问题 | 不推荐 |
| PyQt6 | 与 PySide6 能力相同 | **GPL-3.0 商业授权**（闭源分发需付费） | 排除 |
| 纯 Web（Gradio/Streamlit） | 开发快 | 需要浏览器、体验不像桌面应用、打包体积大 | 排除 |

**结论：PySide6 + PyInstaller。** 语言锁定 **Python 3.12**（pdf2zh 生态与 pdfplumber 兼容性最佳；3.13 部分 wheel 尚不齐）。

## 3. PDF 内核选型（关键决策 D2）

| 能力 | 选中方案 | 许可证 | 说明 |
|---|---|---|---|
| 页面渲染（→ 位图，供 OCR 与预览） | **pypdfium2** | Apache-2.0 / BSD-3-Clause | 基于 Chromium 的 PDFium，C 实现，渲染快质量高，pip 直接装 wheel |
| 文本层 + 精确坐标 + 表格提取 | **pdfplumber**（底层 pdfminer.six） | MIT | 字符级 bbox、字号、字体名，最适合版面重建 |
| PDF 结构读写 / 合并 / 拆分 / 书签 | **pypdf** | BSD-3-Clause | 合并分片、写元数据、操作大纲 |
| 生成新页面内容（回填层） | **reportlab** | BSD-3-Clause | 绘制文本、自动换行、字体嵌入与子集化 |

> ⚠️ **明确排除 PyMuPDF（fitz）**：它是 PDF 处理的事实标准、性能最好，但自 1.24 起为 **AGPL-3.0**（Artifex 双许可）。一旦链接进我们分发的二进制，我方全部源码必须以 AGPL 开源，或向 Artifex 购买商业许可。本项目的目标是"你可自由决定要不要开源"，因此走宽松许可证组合。请确认此取舍（D2）。

**可行性结论**：pypdfium2 + pdfplumber + pypdf + reportlab 的组合，可完整覆盖"渲染 → 提取 → 重建 → 合并"链路，功能上不存在缺口，代价是渲染速度略低于 PyMuPDF（对 OCR 通道每页多约 0.1–0.3 s，可接受）。

## 4. OCR 选型（决策 D4）

| 引擎 | 许可证 | 体积 | 速度（CPU） | 中文精度 | 结论 |
|---|---|---|---|---|---|
| **RapidOCR（ONNXRuntime）** ✅ 默认 | Apache-2.0 | ~15 MB 模型 + ~40 MB ORT | 1–2 s/页 | 良 | **默认内置** |
| PaddleOCR 3.x（PP-OCRv5/v6） | Apache-2.0 | 较大（含 PaddlePaddle 推理或 ONNX） | 数秒/页 | 优（版面/表格/公式齐全） | **可选增强包** |
| Tesseract 5 | Apache-2.0 | 小 | 快 | 中文弱，且需外部二进制 | 排除 |
| EasyOCR | Apache-2.0 | 需 PyTorch（~200 MB+） | 慢 | 良 | 排除（体积） |
| Surya | Apache-2.0 代码 / 权重 OpenRAIL-M（>500 万美元营收需付费） | 需 PyTorch | 慢 | 优 | 排除（许可与体积） |
| Docling（MIT） | MIT | 需 PyTorch | 慢 | 良 | 不采用（重），但其 DocTags 思路可借鉴 |
| Ollama 视觉模型（qwen3-vl / gemma3 / translategemma 支持图像输入） | 依模型条款 | 0（复用 Ollama） | 慢（数秒~数十秒/页） | 优（复杂版面、手写） | **可选高级通道** |

**策略**：默认 RapidOCR 保证"人人可用、开箱即用"；提供「高精度」开关切换到 PaddleOCR（首次使用时按需下载模型，不进安装包）；提供「视觉模型 OCR」开关调用 Ollama 中的多模态模型处理复杂页。三者统一在 `OcrEngine` 抽象接口下。

**图像预处理**：`opencv-python-headless`（Apache-2.0）+ `numpy` + `Pillow`，做灰度、自适应二值化、去噪、霍夫/最小外接矩形去倾斜。

## 5. 翻译模型选型（决策 D3）

调用方式统一为 **Ollama HTTP API**（`/api/chat`、`/api/tags`、`/api/pull`）。以下为 Ollama 上可直接使用、且经过验证的主流选择：

| 模型 | Ollama tag | 体积 | 上下文 | 特点 | 许可 | 建议 |
|---|---|---|---|---|---|---|
| **TranslateGemma 12B** ✅ 首选 | `translategemma:12b` | 8.1 GB | 128K | Google 基于 Gemma 3 的**翻译专用**模型，55 种语言，支持图文输入；同尺寸下翻译质量最佳 | Gemma 输出条款（个人/研究自由；商用需阅读条款） | 默认推荐（8–12 GB 显存/内存） |
| TranslateGemma 4B | `translategemma:4b` | 3.3 GB | 128K | 同上，低配版 | 同上 | 8 GB 内存机器默认 |
| TranslateGemma 27B | `translategemma:27b` | 17 GB | 128K | 质量上限最高 | 同上 | 16 GB+ 显存可选 |
| Qwen3 8B | `qwen3:8b` | ~5.2 GB | 32K+ | 通用模型，中英日韩强，Apache-2.0 商用最宽松 | **Apache-2.0** | **商用场景首选** |
| Qwen3 4B / 1.7B | `qwen3:4b` / `qwen3:1.7b` | 2.6 / 1.3 GB | — | 低配降级 | Apache-2.0 | 低配兜底 |
| Gemma 3 4B/12B | `gemma3:4b` / `gemma3:12b` | 3.3 / 8.1 GB | 128K | 140+ 语言，长上下文利于术语一致 | Gemma 条款 | 备选 |
| Llama 3.1 8B | `llama3.1:8b` | 4.7 GB | 128K | 欧洲语系稳 | Llama 社区许可 | 备选 |
| MADLAD-400 3B | 需自建（非 Ollama 主流） | ~3B | — | 419 语种、Apache-2.0 | Apache-2.0 | 仅作扩展说明 |
| NLLB-200 | 需自建 | 0.6B–54B | — | 200 语种 | **CC-BY-NC（非商用）** | ⚠️ 不推荐，仅提示 |
| Aya / Command-R | `aya-expanse:8b` 等 | — | — | 多语强 | **CC-BY-NC-4.0** | ⚠️ 非商用，不推荐 |

**推荐默认策略**：
- 检测到 ≥16 GB 可用内存 → 推荐 `translategemma:12b`
- 8–16 GB → `translategemma:4b` 或 `qwen3:8b`
- <8 GB → `qwen3:1.7b`
- 界面始终允许手动切换，并标注每个模型的体积与条款提示。

## 6. 其他格式解析

| 格式 | 库 | 许可证 |
|---|---|---|
| DOCX | `python-docx` | MIT |
| PPTX | `python-pptx` | MIT |
| XLSX | `openpyxl` | MIT |
| EPUB | `ebooklib` + `beautifulsoup4` | AGPL? → 用 `ebooklib`（MIT? 需复核）/ 或自研 zip+XML 解析（EPUB 本质是 OPF/XHTML 压缩包） | 
| HTML | `beautifulsoup4` + `lxml` | MIT / BSD |
| SRT/VTT | 自研解析（格式极简） | — |
| 图片 | `Pillow` | HPND |
| ODT/RTF | 自研最小解析 或 `odfpy`（LGPL） | 视情况 |

> EPUB 与 SRT 建议自研轻量解析（各约 150 行），可彻底规避第三方许可证与体积问题。

## 7. 存储与工程组件

| 用途 | 选型 | 理由 |
|---|---|---|
| 进度 / 翻译记忆 / 术语表 | **SQLite**（Python 内置 sqlite3，WAL 模式） | 零依赖、断电安全、天然支持断点续翻 |
| 配置 | JSON（`platformdirs` 定位标准配置目录） | 简单可编辑 |
| 日志 | `loguru` 或标准 logging + 轮转 | 可导出排障 |
| HTTP | `httpx` 或 `requests` | 调用 Ollama |
| 并发 | `concurrent.futures.ThreadPoolExecutor` / Qt `QThreadPool` | IO 密集型为主 |
| 字体 | Noto Sans SC / Noto Serif SC（OFL-1.1），随包分发子集 | CJK 内嵌必需 |

## 8. 可行性结论

| 环节 | 结论 |
|---|---|
| 本地翻译 | ✅ 完全可行，Ollama 已提供标准 HTTP API，无需自研推理 |
| 离线 OCR | ✅ 可行，RapidOCR ONNX 方案成熟且轻量 |
| PDF 版面重建 | ✅ 可行但有难度，是本项目的核心技术难点，需专门的迭代（M2）与测试集（08） |
| 大文件流式处理 | ✅ 可行，属确定性工程，按页 + SQLite 落盘即可 |
| 双平台打包 | ✅ 可行；**注意 macOS dmg 必须在 macOS 环境构建**（见 07） |

**最大不确定性**：PDF 原位回填的排版质量。缓解方式是同时提供 Markdown 降级输出与双语对照输出，并在 M2 阶段用真实样本集建立评分基线。
